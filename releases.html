What's Changed

  • fix(tracing): give serve and worker background work their own traces (swamp-club#2467) (#2763)

Summary

Fixes swamp-club#2467. swamp serve runs inside a swamp.cli span that ends only when serve exits, and the AsyncLocalStorage context manager carried it into every timer serve started. So every poll cycle, scheduled fire and background loop joined one trace per process, which grew to millions of spans under a root that was never exported. This PR gives each unit of background work its own trace, applies the same fix to workers, and fixes span export at process exit.

Serve

  • Poll cycles: each cycle (config, access_data, runtime_data, grants_directory) is the root of its own swamp.serve.poll trace, tagged with swamp.serve.poller. Its sync-gate wait, datastore sync and extension spans (for example S3 getObject) nest under the cycle.
  • Scheduled fires: each swamp.scheduled.fire is a root span. Cron timers are started detached in WorkflowScheduler.register.
  • Other loops: heartbeats, GC, token revalidation, audit flushes, telemetry flush and the fire record reaper start their timers detached and add no spans.
  • Webhook queue: the run queue is detached. A queued run without traceparent used to join the trace of whichever request had started the queue processor.

What's Changed

  • fix(windows): restore Windows Compatibility CI (swamp-club#2879) (#2760)

Summary

Windows Compatibility has failed on every push to main since 2026-09-30. Five tests failed, from three causes:

1. utime → PermissionDenied (3 tests, fails every run). Installs write manifest.yaml as 0o444, which on Windows sets the read-only attribute. copyTreePreservingTimes copies a nested entry's root with Deno.copyFile, which carries the attribute over, and Windows refuses to set times on a read-only file. This also broke real installs: upgrading a parent extension that has a nested entry failed on Windows. Now, if setting the times fails with PermissionDenied on Windows, copyTimes makes the file writable, sets the times, then makes it read-only again.

2. Tar source handle never released (1 test, intermittent). Aborting a pipeThrough signal cancels the source only after the pending write settles. A write into a backpressured DecompressionStream never settles once the consumer stops reading, so the archive file stayed open. untarGz now wraps the source in cancelOnAbort, which cancels the source reader directly when the abort fires. listTarGzEntries passes no signal, so its behaviour is unchanged.

3. Unset HOME (1 test, fails every run). The mixed runtime expressions test read env["HOME"], which Windows runners don't set. It now reads a variable supplied through withMockedEnv.

  • fix(tests): exclude cel-js built-in names from CEL property test identifiers (swamp-club#2500) (#2759)

Summary

Fixes swamp-club#2500, a flake in the scheduled flaky-test detection run.

The CEL evaluator property tests generate variable names, put them in the evaluation context, and expect evaluating the name to return the context value. cel-js binds cel, google and optional itself. Evaluating those names returns the built-in namespace object rather than the context value. Run 36040862015 (ubuntu, seed 847670571) drew cel and got {}a instead of 0a in the embedded interpolation property.

This adds those three names to CEL_RESERVED, the same fix as swamp-club#2054. It only changes the test.

User expressions are not affected. Swamp's CEL contexts only expose fixed top-level names (model, inputs, env, vault, data, file, ...), and none of them collide with the cel-js bindings.

What's Changed

  • feat(serve): read the collective API key from a file (swamp-club#2790) (#2758)

Summary

Fixes swamp-club#2790. Until now, serve read its collective key only from the

SWAMP_API_KEY env var (clubApiKey in serve.ts). That key drives headless

OAuth client registration, admin and allowed-user name lookup, instance

registration and the club heartbeat, so it had to live in the serve process's

environment. This PR lets the key come from a file.

  • SWAMP_API_KEY_FILE: a path to a file that holds the key. It works for

every command that accepts SWAMP_API_KEY.

  • --club-api-key-file <path>: available on swamp serve and

swamp serve check-config. swamp serve daemon enable forwards it as an

absolute path, so the service unit stores the path and never the key. Daemon

units don't inherit the enabling shell's environment, so this flag is how a

daemon gets a key from a file.

The order of precedence is --club-api-key-file, then SWAMP_API_KEY_FILE,

then SWAMP_API_KEY. Setting both env vars is an error. Whitespace around the

key is trimmed. A missing, unreadable, empty or directory path is an error that

names the source and the path, and the path is marked for telemetry redaction.

Changes

  • One place resolves the key. src/infrastructure/persistence/api_key_source.ts

is the only code that reads the key. AuthRepository, whoami, serve's

clubApiKey, check-config, quest and auth login/logout all go through it.
